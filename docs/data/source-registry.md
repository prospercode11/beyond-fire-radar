The normalized import is source version `sarasota.scpa.2026-08-02`, content hash `8b4a3490636c493028df57b231581f9c50880244d20ee923fd73207d0bb9691e`, and property import ID `64e7e421-518b-4ea1-97c5-f3d8701884f0`. This is evidence of a manually supplied prototype snapshot only. It does not establish source terms, legal approval, production authorization, spatial accuracy, or property-match accuracy. Live property polling remains disabled; Sarasota dispatch polling is a separate guarded runtime control.

## Miami-Dade source and parcel download evidence

The Miami-Dade active-call provider uses the county's public [MDFR CAD Active Calls page](https://www.miamidade.gov/firecalls/calls.html). Its parser stores the page's regional table rows (`RCVD`, `FC`, `INC TYPE`, `ADDRESS`, and `UNITS`) as source-preserving observations. The page is refreshed every 60 seconds, but it explicitly describes the display as active calls rather than a complete listing and warns that time, address, incident-type, and unit information can be approximate or change.

The script `scripts/download_miami_dade_property_data.py` downloads the public [Miami-Dade parcel feature layer](https://gisweb.miamidade.gov/arcgis/rest/services/Wasd/GovBound_8_v1/MapServer/0) in object-ID range chunks, retaining GeoJSON geometry, original feature rows, normalized address/property fields, per-feature hashes, and a manifest. The layer reports 596,108 parcel features for the current run and a 1,000-record query limit; the resulting manifest is the authoritative count/hash record for the local artifact. The normalized CSV is an import artifact, not a claim that it contains the Property Appraiser's paid sales history.

The [Miami-Dade Property Appraiser bulk library](https://bbs.miamidade.gov/) remains an explicit access boundary: its public page describes weekly parcel, sales, and building-detail CSVs but requires an account and credits. Those exact CSVs are supported as operator-supplied imports once authorized; the application and download script do not bypass payment, login, or certificate controls.

The Broward snapshot used Florida DOR's 2025 preliminary NAL and SDF files and the 2025 final PIN geometry archive. The source SHA-256 values are NAL `eab63540a0c0e69e82ebb5720ef1bb1018196b8ef61fd18e776510401141cdc8`, SDF `98872f2f51b71ed29081e0caebe146ffa37350c79563539ab635670fd3a99f2`, and PIN `26a9b1a06109ca36dd8681962b736fe70f68a9c443f755d01d687ef625dec494`.

The joined source artifact retained 753,242 NAL rows, 753,206 rows with physical addresses, 95,332 indexed sale rows, and 786,580 PIN geometries. The current property import is `2e807f78-e038-446e-9e6a-5b8909f50185`, source version `broward.dor.2025P+2025F.2026-08-03`, content hash `a71c8a1e428230dba436370579f3f0d2d84e75cf650718b9863cc045d616733c`, with 753,206 accepted rows, 36 rejected rows, and manual attestation/source hashes retained. NAL parcel IDs are joined to PIN `PARCELNO`; SDF contributes the latest indexed sale fields and sale count. The exact source files and transformations remain inspectable through the imported property provenance.

Incident processing is provenance-gated by acquisition mode: `manual_snapshot` and `synthetic_fixture` remain available for the prototype workflow; `live_poll` is accepted only after the runtime approval decision passes. Local development may use the explicit operator basis `explicit_user_permission`; production/staging require a persisted approved `LegalApproval`. This distinction is retained on retrievals and processing runs and surfaced on incident detail responses.

Phase 5 scoring preserves the same provenance boundary. A score may be computed for research/review from current manual or fixture records, but an operational alert requires only explicitly authorized `manual_snapshot` retrievals with an authorization basis, a resolved property match, no contradiction/negative hard gate, and available fit evidence. Synthetic fixtures and live/unauthorized retrievals cannot satisfy that alert gate; this is an application control, not a legal approval.

Phase 6 adds no external provider. The dashboard reads governed incident/retrieval/property/score APIs, distinguishes live-collected Sarasota records from manual/test records, shows the current guarded 15-minute polling status from `/healthz`, and presents safe empty states when no approved record is available. Its incident-map surface has no live GIS feed and must not be read as geospatial evidence.

Phase 7 adds only the internal client-roster workflow source. Client CSV rows are manually supplied internal reference data, not external-source approval evidence. Internal alert delivery is in-app only; email, SMS, phone, and consumer outreach channels are disabled and unimplemented.

Phase 8 and Phase 9 add no external provider. Human outcome labels and funnel events are internal manual reviewer records with identity, timestamp, rationale, idempotency, and audit provenance. Evaluation manifests and training snapshots retain the dispatch acquisition modes used by their cases; synthetic fixtures remain pipeline evidence only, and the `sarasota.outcomes` external row remains unimplemented. Learning artifacts cannot convert a manual record into source approval, cannot activate live polling, and cannot support an accuracy claim without real approved held-out evidence and administrator approval.

Phase 10 adds no source. Storage backend choice (`local` or S3-compatible), raw-payload retention tombstones/pending purge state, audit-chain integrity, backup manifests, and operations metadata are deployment controls around the same governed records. Dispatch and property records retain their acquisition mode and provenance when payload bytes are purged. The later local runtime activation adds a normal-HTTPS Sarasota scheduler with a database lease and 900-second minimum interval; it does not change the source approval gate, infer legal permission, or enable Boca/Broadcastify/property polling.
