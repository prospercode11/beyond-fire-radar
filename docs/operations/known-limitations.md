# Known limitations at v1 closure

- Docker/Colima is unavailable on the implementation host. PostgreSQL/PostGIS and Redis integration tests, managed backup, and real R2 behavior are not claimed as executed.
- No written Sarasota dispatch or property-source approval artifact, production credential, license determination, or legal permission was supplied. Sarasota imports remain manual/file/fixture/replay workflows and live polling remains disabled.
- Repository CSV/JSON/HTML/XLSX/ZIP fixtures are mechanics-only evidence. They do not establish real-world parser coverage, incident classification accuracy, property-match accuracy, scoring quality, calibration, or conversion.
- Production SSO/MFA, enterprise provisioning, secret rotation, external error-tracking hookup, and an operator-owned access review remain deployment gates.
- The Python dependency scan has an exact-ID review list for advisories whose fixes were not available on the current package index or whose affected code path is not used. Re-run the scan before deployment and fail on any new advisory.
- The current local rate limiter is bounded and suitable only for development; production requires Redis readiness.
- The current notification queue is internal and synchronous; no external delivery or consumer outreach exists.
- RPO/RTO, throughput, browser support beyond the inspected Chromium-like environment, and managed-service cost are deployment measurements, not repository claims.
- Error tracking is an integration point (`ERROR_TRACKING_DSN`), not a configured external account.
- Beyond Adjusting fit is a deterministic comparison to the public service profile retrieved on 2026-08-03. It is not a learned conversion model and does not establish damage, coverage, claim validity, willingness to hire, or whether a claim is new, underpaid, or denied. Scores using the older `opportunity-scoring.v1` or `opportunity-scoring.v2` releases retain their prior fit rules for auditability.
- Repeated unchanged dispatch captures are grouped into one evidence event for current classification, map display, and `opportunity-scoring.v4`; raw observations, source-row relationships, source record IDs, and capture counts remain retained for audit. A changed source event ID, event time, wording, taxonomy family, or normalized location forms a separate evidence group.
- Miami-Dade active calls are not a complete incident archive. The public page supplies approximate `RCVD` times and approximate/generalized addresses, can change incident/unit information without showing a full change history, and does not provide a stable event ID. The provider therefore preserves the original row, uses the page date plus `RCVD`, and marks location precision as approximate.
- Broward live dispatch is sourced from eFirstAlert's public third-party table, not an official Broward County dispatch record. The display omits a stable incident ID and calendar date, so the provider preserves the raw row, derives a deterministic event key from the displayed call fields, and date-infers the displayed time from retrieval. Fire/medical mixed calls, medical calls, crashes, blank types, and short codes are retained for review but never promoted to a fire opportunity from apparatus units alone.
- The current score release is `opportunity-scoring.v10`; it requires an explicit fire classification before an opportunity can be scored or listed. Its Beyond Adjusting fit includes a 20% Boca Raton public service-area distance component over a 250 km radius. The anchor is a public geographic center/service-area proxy, not a private residence, and the result is not a probability, damage, coverage, claim-validity, or hiring inference. Missing parcel coordinates leave the source-backed fit component unchanged and record the missing proximity evidence. Current contradiction gates are computed from current grouped observations; historical contradiction evidence remains retained but does not permanently poison a corrected incident projection.
- Property matching is an evidence workflow separate from opportunity scoring, so a non-scoreable incident may still show a current property match run. Only explicit fire classifications, including the generic source-supported `FIRE` label mapped to `General fire` and source-specific fire families such as illegal burning or extinguished-fire investigation, can enter the opportunity queue; the generic label does not establish a structure fire or damage finding. Rescue, hazmat, gas-odor, electrical-hazard, alarm, crash, medical, and unsupported event types remain excluded.
- SQLite local development still serializes writers. WAL, a 30-second busy timeout, an API 503 contention response, and safe web retries reduce transient `needs attention` errors, but PostgreSQL remains the required production concurrency boundary.
- Miami-Dade parcel GIS geometry/attributes are now imported through a resumable public download and are available to the property resolver. The Property Appraiser's exact weekly parcel/sales/building-detail CSVs are account/credit-gated and were not bypassed; complete sales/detail coverage is not claimed until an authorized file is supplied.
- Broward's DOR NAL, SDF, and PIN files are imported as one current manually attested snapshot. A refresh checks every active incident, reclassifies stale evidence, and rematches/rescores only explicit fires whose observations, taxonomy, property snapshot, or current score is incomplete or changed; missing or ambiguous property evidence is retained as a visible abstention rather than silently dropping the fire from the opportunity queue. Repeated refreshes preserve prior score and match history without rewriting unchanged county rows. The first refresh after a new large property import can still be expensive in local SQLite; subsequent unchanged refreshes are short, and concurrent writes remain serialized in-process. PostgreSQL remains the production concurrency boundary.
- The current 71-row opportunity projection contains 26 evidence-based abstentions: 23 source locations are blocks/intersections or otherwise too imprecise for a parcel, two exact addresses do not separate one property candidate sufficiently, and one exact multi-unit address lacks enough evidence to resolve a site or unit safely. Sixteen additional rows are intentionally suppressed by the existing negative-source policy for vehicle, brush, outside, or similar source wording. Changing that policy requires a separate governed scoring decision; it was not treated as a matcher bug.
- The Windows desktop installer is built and smoke-tested on a GitHub-hosted Windows runner because the development host is macOS. A real Windows install/uninstall, startup-after-sign-in, tray, SmartScreen, and in-place update exercise remains required before client handoff.
- The desktop repository and its GitHub Releases must be publicly readable for unauthenticated one-click updates. If the repository remains private, each client would need secure GitHub authentication or a separate public update channel; no GitHub token is embedded in the app.
- The current Windows installer is unsigned unless `WIN_CSC_LINK` and `WIN_CSC_KEY_PASSWORD` are configured in GitHub Actions. Update metadata still supplies the release checksum, but Windows publisher trust and Authenticode verification are not claimed until a signing certificate is configured and tested.
